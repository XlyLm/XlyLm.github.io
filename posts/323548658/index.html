【前端面试】六、工程化

发表于2026-11-19|更新于2026-11-19
|浏览量:

一、常见题

1. 什么是前端工程化，包含哪些方面？

用工程手段把“写代码”变成“可协作、可验证、可交付、可运维”的流程。六个方面：规范化（代码规范、提交规范、目录约定）、模块化（拆分与依赖管理）、构建（编译、打包、优化）、质量保障（类型检查、单测、CI 门禁）、发布部署（制品、灰度、回滚）、可观测（错误与性能监控）。判断工程化做得好不好，看的是“新人上手成本、发布频率、线上缺陷率、故障恢复时间”。

2. 前端模块化经历了怎样的演进？

从全局函数与命名空间（易冲突）→ IIFE 与模块模式（隔离但无依赖管理）→ AMD/CMD（浏览器端异步加载，define/require）→ CommonJS（Node 端同步加载）→ ES Modules（静态结构、编译期可分析、支持 tree shaking、浏览器原生支持）。演进的主线是“依赖声明从隐式变显式、加载从运行时变编译期可分析”，这也直接决定了现代构建工具的能力上限。

3. 脚手架的原理是什么？

本质是“模板 + 交互 + 渲染 + 安装”：用交互式 prompt 收集选项（框架、语言、是否需要 lint/测试）→ 从模板仓库拉取（git clone 或 npm 包）→ 用模板引擎（ejs/handlebars）按选项渲染文件 → 生成 package.json 并安装依赖。进阶能力包括插件化（create-vite 的多模板）、preset 复用、以及升级机制（模板与生成物分离，便于后续同步）。

4. ESLint 的原理是什么，怎么配？

基于 AST 遍历：解析源码 → 生成 AST → 遍历节点并触发规则（每条规则监听特定节点类型，报告 context.report）→ 应用修复（fix）。配置由 parser（解析器，TS 用 @typescript-eslint/parser）、plugins（提供规则集）、rules（开关与等级）构成；ESLint 9 起默认用 flat config（eslint.config.js），不再用 extends 链，而是数组 + 按文件匹配。

5. ESLint 和 Prettier 有什么区别，怎么协作？

职责不同：ESLint 管代码质量与潜在错误（未使用变量、==、hook 规则），Prettier 只管格式（缩进、引号、换行），且格式化能力更强更统一。协作方式是用 eslint-config-prettier 关闭所有与格式冲突的 ESLint 规则、让 Prettier 独占格式化，执行顺序是先 lint 修复再格式化（或反过来但避免互相打架）。

6. Git hooks 怎么用在工程化里？

husky 管理 git 钩子（pre-commit、commit-msg、pre-push）；lint-staged 只对暂存区文件跑 lint 与格式化（避免全量检查太慢）；commitlint 校验提交信息符合 Conventional Commits（feat:、fix:、BREAKING CHANGE:），从而支撑自动生成 changelog 与语义化版本。要点是“本地钩子要快（秒级）”，全量检查留给 CI，否则会被开发者用 --no-verify 绕过。

7. 常见的 Git 工作流有哪些？

Git Flow（develop/release/hotfix 分支齐全，适合有固定发布节奏的重流程团队，缺点是分支管理重）、GitHub Flow（主干 + 功能分支 + PR，简单直接）、Trunk-Based（短生命周期分支、频繁合并主干、靠 feature flag 控制上线，适合高频发布的团队）。选型取决于发布频率与团队规模，而不是“哪个更先进”。

8. Babel 的工作原理是什么？

三阶段：parse（源码 → AST，靠 @babel/parser）→ transform（遍历 AST，插件按 visitor 修改节点）→ generate（AST → 代码 + sourcemap）。preset 是一组插件的集合；执行顺序是插件先于 preset，插件按数组顺序、preset 按逆序。理解顺序很关键，否则会出现“我的插件没生效”或“转换结果不符合预期”。

9. 为什么要 polyfill，browserslist 起什么作用？

转译只能改语法（箭头函数、可选链），改不了运行时缺失的 API（Promise、Array.prototype.at、Object.hasOwn），后者需要 polyfill。browserslist 声明目标浏览器范围，Babel 与 autoprefixer 据此决定转译程度与需要补哪些特性——它是“按需转译”的唯一依据，配错会导致“该转的没转”或“产物过大”。

10. core-js 全量引入和按需引入怎么取舍？

全量（import 'core-js/stable'）简单但体积大；useBuiltIns: 'usage' 按代码实际用到的特性注入，体积小但会污染全局（改写内置原型）；用 @babel/plugin-transform-runtime + core-js-pure 可以避免全局污染（适合库），代价是每个文件可能引入辅助代码。工程惯例：业务应用用 usage，类库用 runtime。

11. 构建工具是怎么演进的？

Grunt、Gulp（基于任务与文件流，本质是“批量执行”）→ Webpack（以模块图为核心，生态完备）→ Rollup（面向库、产物更干净）→ Vite（dev 不打包 + 原生 ESM）、esbuild、SWC、Rspack（Rust）、Turbopack（Rust，增量）。演进方向是“更快的编译内核 + 更细的增量 + dev 与 build 的解耦”，但生态兼容性始终是老工具的价值所在。

12. Monorepo 和 Multirepo 怎么选？

Monorepo（单仓多包）：跨包改动可原子提交、依赖版本统一、代码复用与重构方便、统一 CI 与规范；代价是仓库变大、构建与 CI 需要编排（Nx/Turborepo 的任务图与缓存）、权限粒度粗。Multirepo：边界清晰、权限与发布独立、CI 轻；代价是跨库联动困难（改一个接口要发多个包）、版本漂移。判断标准是“包之间是否有频繁的协同改动”。

13. Monorepo 的构建怎么做才不慢？

靠“任务图 + 缓存 + 只构建受影响的包”：Turborepo/Nx 根据依赖关系推导执行顺序、并行跑无依赖任务；对任务输出做哈希缓存（同输入直接命中，本地缓存加远程缓存可跨机器复用）；用 --filter/affected 只跑被改动的包及其下游。没有这三件套的 Monorepo 会随着包数增长而不可用。

14. 组件库/工具库的产物该怎么构建？

产物要覆盖多种消费方式：ESM（供现代打包工具，支持 tree shaking）+ CJS（兼容旧工具）+ 类型声明（.d.ts）+ 样式文件；package.json 用 exports 声明条件导出（import/require/types）与子路径；sideEffects 标记以支持摇树；按需引入通过“每个组件一个入口文件 + exports 子路径”实现，而不是靠 babel 插件改导入语句。另外要产 sourcemap、做体积检查、跑单测与 API 报告。

15. 版本发布怎么自动化？

用 changesets（按改动写变更说明，自动计算版本号、生成 changelog、批量发布）或 semantic-release（分析 commit 信息自动定版本与发布）。核心是“版本号由变更性质决定”（feat → minor、fix → patch、破坏性 → major），并保证发布前跑构建与测试、发布后打 tag 与通知；Monorepo 要注意“依赖内部包时版本必须同步更新”。

16. 环境与配置怎么管理才安全？

分三层：代码内 .env（本地默认值）、CI 变量（构建期注入）、运行时配置（容器启动注入或配置中心下发，便于“一份镜像跑多环境”）。安全要求：密钥不入库、不进产物、日志脱敏；前端只暴露非敏感配置（VITE_ 前缀），敏感能力一律留在服务端。常见事故是把数据库密码写进 DefinePlugin，直接被打进 JS。

17. Mock 有哪几种方案？

接口契约型（OpenAPI/Mock 定义生成 mock 响应，契约即文档）、拦截型（MSW 在 Service Worker 层拦截，dev/测试/浏览器都能用）、代理型（dev server 中间件按规则返回 mock）。要点是“mock 数据与真实接口结构一致、能用同一份契约驱动类型与 mock”，否则前后端联调时必然返工。

18. 代码质量怎么度量？

分维度：覆盖率（行/分支，注意“高覆盖率不等于高质量”）、复杂度（圈复杂度、函数长度）、重复率、规范违规数、类型覆盖（any 占比）、技术债趋势。工具链是 ESLint + 单测覆盖率报告 + SonarQube 类平台。关键是把指标做成门禁（新增代码覆盖率不得下降），否则度量只是报表。

19. 性能预算（performance budget）怎么落地？

在构建产物层面设阈值：入口 chunk 体积、总产物体积、关键资源数量、图片总量；用 size-limit/bundlewatch 在 CI 里比较主分支，超阈值直接失败；配合 bundle-analyzer 看增量来源。运行时可加 Lighthouse CI 对 LCP/TBT 设阈值。意义是“把性能从口号变成每次提交都要付的代价”。

20. 前端可观测性在工程化里怎么落位？

三块：错误（全局异常 + Promise + 资源错误，带版本号与用户环境）、性能（PerformanceObserver 采集核心指标）、行为埋点。工程要点：采集 SDK 要轻、上报用 sendBeacon 并采样限流、sourcemap 与 release 版本关联（生产用 hidden-source-map，map 只上传到监控平台）、告警规则与值班流程。没有版本号的监控数据无法定位问题，这是最常见的设计缺失。

二、难题

1. ESLint 为什么慢，flat config 改变了什么？

慢的原因：需要完整解析 AST（TS 项目还要构建 type program，开销最大）、插件规则数量多、文件全量扫描。flat config 的变化是取消 extends 隐式链，改成可显式组合的数组、按文件 glob 匹配、规则来源清晰（便于定位“这条规则谁开的”），也让共享配置更容易审计。加速手段：--cache、lint-staged 只查暂存文件、type-aware 规则单独跑一个更慢的流水线、或迁移到 Rust 实现（oxlint、Biome）。

2. Babel 插件与 preset 的顺序为什么容易出错？

规则是“插件先执行、preset 后执行；同类内部插件按数组正序、preset 按逆序”。因此同一个语法被两个插件处理时，谁先谁后会产生完全不同的 AST；把插件塞进 preset 又会改变相对顺序。实践中应把“必须最先/最后执行的转换”显式写在 plugins 数组的两端，并用 @babel/helper-plugin-utils 明确 visitor 的 enter/exit，不要依赖运气。

3. 为什么 Babel 处理过的代码 tree shaking 会失效？

tree shaking 依赖 ESM 静态结构，Babel 默认把 import/export 转成 CJS（modules: 'commonjs'），变成运行时赋值，构建工具无法静态判断哪些导出被使用。解决办法是设置 modules: false 保留 ESM，由 Rollup/Webpack 负责模块处理；另外辅助函数（_defineProperty 等）若不抽离，也会造成重复代码而非可摇树的冗余。

4. Monorepo 的远程缓存是怎么工作的？

每个任务（如 build）的输入（源码、依赖版本、配置、环境变量白名单）被哈希成一个 key；执行过就存“key → 产物 + 日志”到本地缓存，命中则直接还原产物并回放日志（跳过执行）。配置远程缓存（如 Turborepo 的 remote cache、Nx Cloud）后，CI 与不同开发机共享同一份缓存，于是“没改的包在所有机器上都不重新构建”。风险是缓存正确性：输入哈希必须覆盖所有影响输出的因素（漏了某个环境变量就会命中错误缓存）。

5. 组件库的 exports 与按需引入怎么设计才正确？

exports 一旦声明，就等于封闭了其他子路径，因此要显式列出所有对外入口（.、./es/*、./style.css 等），并用条件导出区分 import/require/types；按需引入的正确实现是“每个组件独立入口文件 + 模块级 sideEffects 标记”，让打包工具自然摇树，而不是靠 babel-plugin-import 去改源码导入路径。还要注意 types 条件必须指向与格式匹配的声明文件（ESM 用 .d.mts/types 字段配置），否则 TS 会判定为不可用。

6. CI 里怎么做体积门禁与增量分析？

两步：一是与基线对比（检出主分支构建或直接拉取基线统计，比较各 chunk 的体积增量，超过阈值失败）；二是归因（产物里注入模块来源统计，或对两次构建的 stats.json 做 diff，定位到具体新增依赖）。难点在于构建必须可复现（否则体积波动来自环境），所以要固定 Node 版本、锁定依赖、禁用随机与时间戳；对“合理的必要增长”要有审批通道，否则团队会习惯性调高阈值。

7. 工程化怎么量化收益？

四个可观测指标：构建时长（本地与 CI 的 P50/P95）、发布频率与发布耗时（从合并到上线的 lead time）、线上缺陷率与回滚率、故障恢复时间（MTTR）。改进要能对应到指标变化：引入缓存后 CI 时长下降多少、加类型检查后线上类型错误下降多少。没有基线的“工程化改造”很容易变成过度设计（这也是为什么先度量再优化）。

8. 微前端在工程化层面要解决哪些问题？

四个层面：构建独立（子应用独立构建与发布，不互相阻塞）、依赖共享（同一框架只加载一份，需版本协商与单例约束，否则出现多实例问题）、样式与运行时隔离（沙箱、样式前缀、全局变量冲突）、治理（统一路由约定、鉴权与埋点入口、公共依赖升级策略）。落地顺序建议是“先拆构建与发布、再谈运行时隔离”，很多团队失败在“为了技术炫技引入微前端，却没有独立的发布节奏需求”。

【前端面试】九、部署和代理
一、部署1、常见题1. 前端部署的完整流程是什么？分为五步：拉取代码 → 安装依赖（依据 lockfile 保证可复现）→ 构建（注入环境变量、生成带 hash 的产物）→ 把产物分发到目标（Nginx、对象存储或 CDN，或构建镜像）→ 刷新缓存并验证。关键原则是「构建一次，多环境复用同一制品」，即同一份产物依次经过测试、预发、生产，避免“每个环境各构建一次”导致行为漂移。验证包括健康检查、版本号核对与冒烟测试。 2. 前端静态资源一般怎么托管？常见三种：Nginx 自建（可控、成本低，适合内网与中小项目）、对象存储加 CDN（主流方案，天然抗量、就近分发、支持大文件与图片处理）、容器化（打成 Nginx 镜像由 K8s 调度）。选型看流量规模、是否需要灰度、以及运维成本；大流量静态站点基本都会用 CDN，Nginx 只作为回源或兜底。 3.
