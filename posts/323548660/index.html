【前端面试】八、调试

发表于2026-11-19|更新于2026-11-19
|浏览量:

一、常见题

1. 前端调试的主要手段有哪些？

六类：console 输出（快速验证，适合定位“有没有进来”）、断点（精确停在现场看变量与调用栈）、日志与埋点（线上无法断点时靠面包屑还原路径）、二分法（git bisect 定位引入问题的提交）、最小复现（剥离无关代码构造可复现 demo）、以及工具辅助（Network/Performance/Memory 面板、抓包、真机远程调试）。关键原则是“先缩小范围再深入”，而不是一上手就逐行读代码。

2. DevTools 各个面板分别解决什么问题？

Elements（DOM 与样式，看谁覆盖了样式）；Console（日志与运行时表达式）；Sources（断点、调用栈、Overrides、Snippets）；Network（请求、时序分解、限速模拟、重放）；Performance（火焰图，查卡顿与帧耗时）；Memory（堆快照、分配时间线，查泄漏）；Application（localStorage/Cookie/Cache/SW）；Security（证书与混合内容）；Lighthouse（质量评分）。

3. 断点有哪些类型？

行断点（默认）、条件断点（右键设置条件，只在满足时停）、日志断点（logpoint，不暂停只打印，适合循环里的高频代码）、DOM 断点（子树修改/属性修改/节点删除）、事件监听断点（按事件类型，如 click、keydown）、XHR/fetch 断点（按 URL 断在请求发起处）、异常断点（Pause on exceptions，可勾选仅在未捕获时暂停）。此外支持 debugger 语句与“忽略第三方库”（Ignore List，避免停进依赖内部）。

4. 断点打不上/停不到位置怎么办？

三类原因：代码与产物不一致（sourcemap 缺失或错位，实际执行的是转译后代码）、代码根本没执行（被条件分支、缓存、或废弃入口跳过）、位置在异步或宏任务里（需要开启异步调用栈）。排查方式：改用 debugger 或 logpoint 验证是否执行到、在 Sources 里确认映射文件、检查 Ignore List 是否把该文件忽略了、确认没有命中本地缓存（硬刷新）。

5. Network 面板的 Timing 怎么看？

分解为：Queueing（排队，受并发上限影响）、Stalled（等待可用连接）、DNS Lookup、Initial Connection（TCP 握手）、SSL（TLS 协商）、TTFB（等待服务端首字节，反映服务端与网络往返）、Content Download（下载）。判断归属很直接：TTFB 大是服务端慢，Content Download 大是资源大或带宽低，Queueing/Stalled 大是并发被占满（HTTP/1.1 同域 6 个连接）。

6. Network 面板还有哪些实用功能？

限速模拟（Slow 3G 等，用于弱网复现）、Block Request URL（屏蔽某资源验证依赖关系）、重放请求（右键 Replay XHR / Copy as fetch）、查看 Initiator（谁发起了这个请求，沿调用链定位代码）、按类型/状态过滤、Preserve log（跨页面保留记录，定位跳转前的请求）、以及对比多次请求的 Size（是否命中缓存）。排查接口问题固定看四处：状态码、请求头、响应体、CORS 头。

7. console 有哪些常被忽略的能力？

console.table（结构化数组/对象）、console.dir（展开对象细节）、console.time/timeEnd（粗粒度耗时）、console.count（统计执行次数）、console.group/groupEnd（折叠分组）、console.trace（打印调用栈）、console.assert（条件为假时输出）、以及格式化占位符（%c 加样式、%o 展开对象）。定位偶现问题时，把关键路径加上 count 与 trace 往往比断点更有效。

8. 线上代码不能改，怎么调试？

手段有四种：Sources → Overrides（把线上资源映射到本地副本，改完立即生效，刷新后仍生效，适合验证“改这一行是否能修好”）；Snippets（在页面上下文里跑一段脚本，如批量查看 DOM、调用内部方法）；条件断点 + 异常断点（只停在你关心的现场）；以及日志级别动态下发（服务端配置开关，让线上 SDK 输出更多信息）。注意这些都只能临时验证，真正的修复要走发布流程。

9. 样式问题怎么系统排查？

四步：在 Elements → Styles 里看规则是否被划掉（谁覆盖的、来自哪个文件）、看 Computed 的最终值与其来源、检查是否被 !important 或更高权重规则压制、确认是否受层叠上下文（z-index 与 transform/opacity 创建的上下文）影响。层叠问题要沿祖先链找“谁创建了上下文”，而不是继续加 z-index；布局问题优先看是否有未清除的浮动、min-width 撑破、box-sizing 差异。

10. 接口异常怎么定位？

按顺序看：请求是否发出（Network 有无记录）、状态码（4xx 是客户端问题、5xx 是服务端问题、0 或 (failed) 多为网络/CORS/证书）、请求头（Content-Type、鉴权、Origin）、响应体（业务错误码与消息）、以及 Timing（是否超时）。CORS 失败要单独看预检请求是否返回 204 且头齐全；超时要区分“服务端慢”与“客户端主动 abort”。

11. 内存泄漏怎么查？

三步：用 Performance 的 Memory 勾选记录，观察内存曲线是否阶梯上升不回落；用 Memory → Heap Snapshot 做“操作前/操作后/再操作一次”三次快照，在 Comparison 视图看“两次之间新增且未释放”的对象类型；点开对象的 Retainers 看引用链，找到阻碍回收的那条路径（常见是全局数组、未移除的监听、未清理的定时器、detached 的 DOM 树）。要区分“容量上涨”与“泄漏”：GC 后能回落就不是泄漏。

12. 卡顿怎么查？

用 Performance 录制一段操作，看主线程火焰图里的长任务（超过 50ms 的黄色块），拆解其 self time（自身执行）与子调用，定位到具体函数；同时看是否有频繁的 Layout/Paint（强制同步布局）、GC 事件（内存压力）、以及帧是否持续超过 16.7ms。优化方向：把长任务切片、把纯计算搬到 Worker、减少渲染量（虚拟列表）、避免在滚动/输入里做重活。

13. 线上问题定位的整体思路是什么？

固定信息面：版本号与发布记录（最近是否变更）、用户环境（机型、浏览器、网络、地区）、监控数据（错误率、上报量突降=白屏特征、接口失败率）、可复现性（本地能否复现、是否只在小比例用户出现）、灰度对照（新旧版本指标对比）。经验上“发布后立刻出现的集中问题”优先怀疑版本与缓存，“缓慢出现且分散的问题”优先怀疑数据与兼容性。

14. 真机与移动端怎么调试？

Android：开启 USB 调试 + chrome://inspect 映射设备页面；iOS：Safari 的“开发”菜单选择设备（需在手机上信任）；无 USB 时用 vConsole/eruda 在页面内显示日志与网络；网络层用 Charles/Stream 抓包并配置代理。注意 HTTPS 抓包需要设备信任抓包工具的根证书，而开启了证书固定的 App 无法抓包。

15. 抓包工具的原理是什么？

抓包工具本质是中间人代理：设备把请求发给代理，代理与目标服务器建立连接并转发，因此能记录全部请求响应。HTTPS 之所以能解密，是因为代理用自己的根证书动态签发目标站点的证书，设备信任该根证书后即接受了这次“中间人”。这也是为什么必须安装并信任证书，以及为什么客户端做了证书固定（certificate pinning）时抓包会失败。

16. React / Vue 项目专用调试怎么用？

框架 DevTools 能看组件树（层级、props、状态）、直接修改状态验证渲染逻辑、查看 Hooks 依赖与更新原因、以及性能分析（React Profiler 的火焰图能看出“哪个组件渲染耗时最多、为什么重渲染”）。Vue DevTools 还能看 Pinia/Vuex 状态变化时间线。定位“为什么这个组件重渲染”时，先用 Profiler 拿到可疑组件，再去核对 props 引用与依赖数组，比盲猜高效得多。

17. sourcemap 在调试中起什么作用？

它把压缩/转译后的代码位置映射回源码位置，让调用栈与断点落在正确的行列。前提是 map 文件可被 DevTools 访问（sourceMappingURL 或 Sourcemap 响应头）。生产环境常用 hidden-source-map：生成 map 但不写引用，仅上传到监控平台用于栈还原；若 stack trace 里全是 a1b2c3.js:1:23456，就是没有可用 map 或版本不匹配。

18. 二分法定位问题怎么做？

两种二分：代码二分（注释掉一半逻辑/关掉一半功能看问题是否消失）与提交二分（git bisect 标记好/坏提交，自动缩到引入问题的那个 commit）。适用前提是“问题能稳定复现”，因此先造一个可复现的最小输入很关键。配合“最小复现”原则：不断剥离无关依赖、配置与数据，直到剩最小可运行片段，问题通常自己就暴露了。

二、难题

1. 生产环境完全不暴露 sourcemap，还能定位报错吗？

可以，但要用“上传而非公开”的方式：构建时生成 hidden-source-map，在发布流水线里把 map 上传到监控平台并以版本号（release）索引，前端只上报压缩后的栈与 release。平台侧在展示时做栈还原。前提是版本号必须准确绑定（同一 release 的 map 才能还原），且 map 访问要鉴权（map 泄露等于源码泄露）。若连这套都没有，退而求其次是在产物里保留函数名（关闭混淆但保留压缩）以提升可读性。

2. 火焰图上的 self time 和 total time 有什么区别？

total time 是“这个函数及其所有子调用的总耗时”，self time 是“该函数自身执行的时间（不含子调用）”。定位瓶颈要看 self time：它大说明这段代码本身慢（大循环、复杂计算、正则回溯）；total time 大而 self time 小说明时间花在下游（继续往下钻）。常见误判是盯着入口函数的 total time 就断言“这个组件慢”，实际瓶颈在某个深层工具函数。

3. 内存快照对比时该关注什么？

关注三件事：新增对象数量（两次快照之间新增且仍存活的实例，按构造函数排序，突然变多的一类就是嫌疑）、占比与大小（字符串与数组常是大头，注意 (string) 与 system/Context）、retainers 链（从嫌疑对象追到 GC 根，路径上的第一个“不该存在”的引用就是泄漏源）。技巧是“操作前后各拍一次，再重复操作拍第三次”：第二次到第三次仍在增长的对象几乎就是泄漏，能排除“缓存预热”这类假阳性。

4. 偶现问题（无法稳定复现）怎么推进？

四条并行：加可观测性（关键分支打点、错误上下文、耗时与入参，用采样控制量）、扩大样本（让更多用户环境上报，按机型/网络/版本分组统计，找相关性）、构造环境（限速、延迟抖动、内存压力、并发注入，把“偶现”变成“高概率”）、灰度对照（新旧版本同环境对比，确认是否版本引入）。同时建立“复现率”指标：从 1/1000 提到 1/10，问题基本就能定位；长期不复现的问题要接受“先用监控兜住、后续再优化”的现实。

5. 弱网下的竞态与超时怎么复现与验证？

用 DevTools 的限速（自定义上下行与延迟，加入抖动）、加上“随机失败”注入（拦截部分请求返回 500/超时）、以及并发压测（脚本一次性发多个请求）。观察点：请求是否被正确取消、旧响应是否覆盖新状态、重试是否叠加成风暴、加载态是否卡死。修复后用同样的注入手段回归，确认“取消 + 版本号丢弃 + 退避重试”三条都生效。

6. Worker 与 Service Worker 的调试难点在哪？

Worker：有独立执行上下文，主线程断点不会停在里面，要在 Sources → Threads 里切换到对应 worker 线程下断点；错误不会冒泡到主线程（需自己在 onerror 与 messageerror 里上报）；postMessage 是结构化克隆，传大对象会有隐藏开销。Service Worker：生命周期（install/activate/update）与缓存策略容易造成“改了代码但页面还是旧的”，调试要勾选 Update on reload、必要时 Unregister 后重装，并注意它接管后所有请求都经过它，出错表现为“全站资源异常”。

7. 线上“部分用户白屏”怎么快速分层？

先分“全量/部分”：全量优先查发布与 CDN（HTML 被缓存、证书过期、发版顺序错导致资源 404）；部分优先按维度切分（机型/浏览器版本/地区/网络运营商/是否灰度用户）。再看监控特征：错误上报量骤增（代码异常）、上报量骤降（页面根本没启动，典型白屏）、接口成功率下降（首屏依赖失败）。手段：让受影响用户打开带 ?debug=1 的页面收集环境信息、对比灰度组、必要时先回滚再查根因。主线是“先止血、后归因、再修复”。

8. 如何建立团队的调试规范，避免“人人靠猜”？

四件事：统一入口（错误监控 + 版本号 + 面包屑日志，任何人拿到用户反馈都能自查）；统一符号（sourcemap 上传与 release 关联，栈必须可读）；统一手法（按“版本/环境/可复现性/灰度”四象限先分类，再选工具，禁止无假设地逐行读代码）；统一沉淀（每个线上问题写复盘：现象、定位路径、根因、修复、防复发措施）。规范的价值在于把“个人经验”变成“团队可复用的排查路径”，也让新人的定位时间从小时级降到分钟级。

一、浏览器1、常见题1. 浏览器的多进程架构是怎样的？主进程（Browser，负责标签页管理、地址栏、窗口与网络调度）、渲染进程（Renderer，负责 HTML/CSS/JS 解析与页面渲染，每个标签页一个、同站点可能共享，跨站点则强制隔离）、GPU 进程（负责合成与绘制加速）、网络进程（负责请求与缓存）、插件/工具进程。多进程的价值是稳定性与安全隔离（一个页面崩溃不拖垮整个浏览器，站点隔离用于缓解 Spectre 这类侧信道攻击），代价是内存占用高。 2. 从输入 URL 到页面显示经历了什么？用户输入 → 判断是搜索还是 URL（浏览器进程）→ DNS 解析 → TCP/TLS 建立连接（HTTP/2 复用、HTTP/3 走 QUIC）→ 发送请求（带缓存校验、Cookie）→ 服务端返回 → 浏览器解析 HTML 构建 DOM、请求子资源 → 解析 CSS 构建 CSSOM → 合成渲染树 → 布局 → 绘制 → 合成上屏。渲染阶段的关键是“HTML 解析是流式的、CSS 与 JS 可能阻塞”。 3. 渲染流程分...

一、部署1、常见题1. 前端部署的完整流程是什么？分为五步：拉取代码 → 安装依赖（依据 lockfile 保证可复现）→ 构建（注入环境变量、生成带 hash 的产物）→ 把产物分发到目标（Nginx、对象存储或 CDN，或构建镜像）→ 刷新缓存并验证。关键原则是「构建一次，多环境复用同一制品」，即同一份产物依次经过测试、预发、生产，避免“每个环境各构建一次”导致行为漂移。验证包括健康检查、版本号核对与冒烟测试。 2. 前端静态资源一般怎么托管？常见三种：Nginx 自建（可控、成本低，适合内网与中小项目）、对象存储加 CDN（主流方案，天然抗量、就近分发、支持大文件与图片处理）、容器化（打成 Nginx 镜像由 K8s 调度）。选型看流量规模、是否需要灰度、以及运维成本；大流量静态站点基本都会用 CDN，Nginx 只作为回源或兜底。 3.
